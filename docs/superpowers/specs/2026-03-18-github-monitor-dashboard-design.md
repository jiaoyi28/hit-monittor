# GitHub 个人监控台 V1 设计文档

## 1. 背景与目标

本项目是一个运行在 Windows 本机环境中的个人 Web 前后端应用，用于追踪指定 GitHub 公开仓库的动态，并通过大模型对热点 issue、热点 PR 和 release 说明进行分析与总结。

V1 的目标不是替代 GitHub，而是在个人观察清单场景下提供一个高信息密度的前置筛选与判断层，让用户在短时间内知道哪些仓库、哪些事件最值得深入查看。

## 2. V1 范围

### 2.1 纳入范围

- 运行环境为 Windows 本机
- 单用户使用，不需要登录
- 仅支持 GitHub 公开仓库
- 个人观察清单模式，仓库规模约 5 到 20 个
- 以仪表盘浏览为主，而不是日报或推送
- 后台定时抓取 GitHub 数据
- 后台定时执行 AI 预分析
- 模型接口以 OpenAI 为主，同时支持兼容 OpenAI 风格的 `base_url`
- 使用 SQLite 作为本地数据库，数据库文件目录固定为 `D:\sqlite`

### 2.2 不纳入 V1 范围

- GitHub 私有仓库访问
- 多用户与账户体系
- X、QbitAI、OpenAI Blog、Anthropic Blog 等外部资讯源追踪
- 邮件、Webhook、桌面通知等推送能力
- 向量检索、RAG、知识库问答
- 自动发现并新增仓库到观察清单

## 3. 技术约束与选型

### 3.1 前端

- 包管理与构建：`npm`
- 应用形态：单页 Web 应用
- UI 技术栈：`Tailwind CSS + shadcn/ui`
- 建议框架：`React + Vite`

### 3.2 后端

- 语言与依赖管理：`Python + uv`
- API 服务：`FastAPI`
- ORM 与数据建模：`SQLAlchemy`
- 数据库：`SQLite`
- 调度方式：后端进程内任务调度

### 3.3 外部集成

- GitHub：使用公开 API 拉取 issue、PR、release 数据
- 大模型：使用 OpenAI 接口协议，支持自定义 `api_key`、`model` 和 `base_url`

## 4. 总体架构

系统采用前后端分离架构，但整体以本机部署和本机运行体验为核心。

### 4.1 前端应用

前端负责：

- 展示总览仪表盘
- 展示仓库列表
- 展示仓库详情页
- 展示配置页
- 调用本地后端 API 获取预先抓取和预先分析好的数据

前端不直接访问 GitHub，也不直接调用模型接口。

### 4.2 后端 API 服务

后端负责：

- 提供仓库、issue、PR、release、AI 分析结果相关 API
- 提供配置读取与更新 API
- 提供任务状态与手动刷新 API
- 协调抓取流程、清洗流程、分析流程与数据落库

### 4.3 后台任务层

后台任务独立于页面访问周期运行，包括：

- GitHub 元数据抓取
- 数据清洗与归一化
- 热点候选筛选
- AI 预分析
- 任务状态记录

### 4.4 本地数据库

SQLite 既承担持久化存储，也承担本地缓存和历史基线作用。

数据库文件目录固定为 `D:\sqlite`。实现时应允许应用在该目录下创建项目专用数据库文件，例如 `D:\sqlite\hit-monittor.db`。

### 4.5 模块划分

后端建议拆分为以下模块：

- `connectors`：GitHub 数据抓取
- `pipeline`：数据清洗、归一化、入库
- `analysis`：提示词组织、模型调用、结构化结果生成
- `app/api`：面向前端的 HTTP API
- `scheduler`：抓取和分析任务调度

这种边界有利于后续扩展外部资讯源，而不需要重构整个系统。

## 5. 核心页面设计

### 5.1 总览仪表盘

首页用于帮助用户在 30 秒内知道当前最值得关注的内容，建议包含：

- 最近最活跃的仓库
- 今日或近 7 天热点 issue
- 今日或近 7 天热点 PR
- 最新 release 与重要 release 摘要
- AI 给出的本周重点关注仓库或主题

### 5.2 仓库列表页

仓库列表页用于管理和浏览个人观察清单，建议支持：

- 按最近活跃度排序
- 按 issue、PR、release 活跃类型筛选
- 按是否有新 release 筛选
- 按是否存在高热讨论筛选
- 展示每个仓库的 AI 标签，例如“PR 活跃”“发布密集”“Issue 讨论升温”

### 5.3 仓库详情页

仓库详情页按仓库维度展示分析结果，建议包含：

- 仓库级 AI 总结
- 热点 issue 区块
- 热点 PR 区块
- release 区块
- 对每项内容提供跳转原始 GitHub 页面链接

仓库级 AI 总结至少覆盖：

- 最近在忙什么
- 当前讨论重心是什么
- 近期值得持续跟进的点是什么

### 5.4 配置页

配置页仅保留必要设置，包含：

- GitHub 仓库清单维护
- 抓取时间间隔配置
- AI 分析时间间隔配置
- OpenAI 或兼容服务配置：`api_key`、`base_url`、`model`
- AI 摘要长度偏好
- 手动触发刷新或重分析
- 最近任务状态与错误信息

## 6. 用户操作流

典型使用路径如下：

1. 用户打开首页，快速查看当前最值得关注的仓库和事件。
2. 用户从热点列表或仓库列表进入某个仓库详情页。
3. 用户快速阅读 issue、PR、release 的 AI 摘要和趋势判断。
4. 当某项内容值得深入查看时，用户跳转到 GitHub 原始页面继续阅读。

这个流程强调“先筛选，再深入”，而不是让用户在本应用中完整替代 GitHub 阅读体验。

## 7. 数据模型

### 7.1 `repositories`

用于保存观察清单中的仓库信息，建议字段包括：

- `owner`
- `name`
- `full_name`
- `description`
- `html_url`
- `enabled`
- `last_synced_at`
- `last_analyzed_at`
- `created_at`
- `updated_at`

### 7.2 `issues`

用于保存 issue 基础信息与分析输入材料，建议字段包括：

- GitHub 对象 ID
- 所属仓库 ID
- 标题
- 状态
- 标签
- 评论数
- 作者
- 创建时间
- 更新时间
- 原始链接
- 正文摘要或清洗后的分析输入文本

### 7.3 `pull_requests`

用于保存 PR 基础信息与分析输入材料，建议字段包括：

- GitHub 对象 ID
- 所属仓库 ID
- 标题
- 状态
- 评论数
- review 活跃度
- 作者
- 是否已合并
- 合并时间
- 创建时间
- 更新时间
- 原始链接
- 清洗后的分析输入文本

### 7.4 `releases`

用于保存 release 信息，建议字段包括：

- GitHub 对象 ID
- 所属仓库 ID
- 版本号或 tag
- 标题
- 发布时间
- 原始 release note
- 清洗后的 release 摘要文本
- 原始链接

### 7.5 `analysis_results`

用于保存模型输出，按对象类型和分析类型区分。建议支持：

- 仓库级总结
- issue 热点分析
- PR 热点分析
- release 摘要分析
- 趋势判断

每条分析结果建议保存：

- 分析对象类型
- 分析对象 ID
- 模型名称
- 分析版本
- 结构化结果 JSON
- 生成时间
- 失效时间或下次建议重算时间

### 7.6 `sync_jobs`

用于记录任务运行状态，建议字段包括：

- 任务类型
- 目标范围
- 开始时间
- 结束时间
- 执行状态
- 错误信息
- 处理数量
- 配置快照

### 7.7 `app_settings`

用于保存产品配置，至少包含：

- 抓取时间间隔
- AI 分析时间间隔
- 分析候选数量上限
- OpenAI `api_key`
- OpenAI `base_url`
- OpenAI `model`
- AI 摘要长度偏好

## 8. 抓取与分析策略

### 8.1 抓取策略

系统需要支持对抓取时间间隔进行配置，配置项保存在数据库中，并由调度器动态读取，而不是写死在代码中。

抓取任务的职责包括：

- 拉取仓库元数据
- 拉取近期 issue
- 拉取近期 PR
- 拉取近期 release
- 更新本地活跃度基线

### 8.2 AI 分析策略

系统需要支持对 AI 分析时间间隔进行配置，配置项保存在数据库中，并由调度器动态读取。

分析任务需要与抓取任务解耦，允许：

- 高频抓取、低频分析
- 手动立即触发分析
- 对单仓库或全量仓库执行重分析

### 8.3 候选筛选

为了控制模型成本与提升分析质量，V1 不对所有对象无差别送模，而是先筛选候选热点。候选筛选可以参考以下信号：

- 最近更新时间
- 评论数
- review 数
- 标签类型
- 是否刚发布新版本
- 是否持续多天活跃

### 8.4 AI 输入整理

送入模型前，需要将 GitHub 原始数据整理为统一结构，建议至少包含：

- 基本元信息
- 标签与状态
- 时间线摘要
- 讨论摘要
- release note 摘要

### 8.5 AI 输出结构

模型输出需要结构化，避免只保存自由文本。建议至少生成：

- 热点等级
- 核心摘要
- 值得关注原因
- 可能反映的项目方向
- 是否建议持续观察

## 9. 错误处理

### 9.1 抓取错误

例如 GitHub API 超限、网络波动或仓库不存在。处理策略：

- 本轮任务标记失败
- 保留上次成功抓取的数据
- 在任务页或配置页显示错误信息

### 9.2 AI 分析错误

例如 `api_key` 无效、`base_url` 不可达、模型超时。处理策略：

- 本轮分析结果标记失败
- 不覆盖已有可用历史分析结果
- 在配置页明确展示错误上下文

### 9.3 数据清洗错误

例如个别 release note 格式异常。处理策略：

- 跳过单条异常对象
- 记录日志和任务明细
- 不影响整批任务完成

## 10. 调度设计

V1 采用后端进程内调度，而不是依赖外部 Windows 计划任务。

调度器需要具备以下能力：

- 启动时读取配置
- 独立维护抓取任务与分析任务
- 展示上次执行时间、下次计划时间、最近一次错误
- 支持配置变更后动态生效
- 支持用户在界面上手动触发立即执行

这种方式更符合本机单用户工具的维护成本要求。

## 11. 安全与配置

虽然 V1 是单用户本机应用，但仍应保证：

- `api_key` 不写死在代码中
- 敏感配置通过本地配置或环境变量管理
- 前端不直接暴露敏感密钥

对于 `SQLite` 数据库路径，需要在启动时检查 `D:\sqlite` 是否存在；若不存在，可在用户明确授权的情况下自动创建，或在启动检查中给出明确提示。

## 12. V2 扩展方向

当 V1 稳定后，建议优先扩展：

- GitHub 私有仓库支持
- 外部资讯源追踪能力
- 多模型支持
- 周报或日报导出
- 统一主题视图，将 GitHub 热点与外部资讯热点合并展示

## 13. 成功标准

如果满足以下条件，可认为 V1 达到目标：

- 用户可以维护自己的 GitHub 公开仓库观察清单
- 系统可按配置时间间隔自动抓取 issue、PR、release 数据
- 系统可按配置时间间隔自动执行 AI 预分析
- 首页能快速展示当前最值得关注的仓库和事件
- 仓库详情页能给出热点摘要和趋势判断
- 模型配置可替换为 OpenAI 兼容 `base_url`
- 本机 Windows 环境可稳定运行，不依赖外部部署
